# 代码开发规范

本规范约束本仓库的源码结构、修改方式和检查口径，供人工与代理接手开发时共同遵守。任务分派、PR 与合并流程见 [Issue 并行开发与交付](development.md)；执行语义与数据口径以该文和 [用量、额度与耗时账本](observability.md) 为准。规范与用户当次明确要求冲突时，以用户要求为准，并在交付说明中写明。

## 1. 目录与运行位置

| 目录 | 运行位置 | 职责 |
| --- | --- | --- |
| `src/` | 本机 DSH 插件进程 | `BridgeBackend` 编排、协议客户端、历史投影、计时与用量投影、纯规则模块 |
| `remote/` | VPS 上的父服务与每设备 worker | WebSocket 服务、worker 生命周期、SDK 调用、观测账本与额度采样 |
| `plugin/` | DSH 插件入口、预设、兼容层、UI | 与 DSH 原生接口对接；UI 源码在 `plugin/ui/client/*.mjs` |
| `scripts/` | 本机或 CI | 构建、更新、隔离启动、回归和只读查询工具 |
| `test/` | 本机 Node 与 CI | `node:test` 用例；当前 0.2.2-rc.1 原生用例在 CI 的 Windows Electron 中执行 |

- `src/` 不得依赖 `remote/`。两端共享的纯规则（如 schema、计量换算）放在 `src/`，由 `remote/` 引用。
- `remote/` 模块不得读取客户端用户数据；`src/` 不得假设 VPS 文件系统路径。

## 2. 生成文件与兼容副本：禁止手改

| 文件 | 来源 | 修改方式 |
| --- | --- | --- |
| `plugin/ui/client.js` | `plugin/ui/client/*.mjs` | 改源码后运行 `node scripts/build-client.mjs`，提交前用 `--check` 确认一致 |
| `plugin/index.mjs` | `plugin/index.mts` | 改 `.mts` 后运行 `node scripts/build-plugin.mjs` |
| `plugin/compat/agent-loop.original.mjs`、`plugin/compat/provenance.json` | 官方 rc.5 包 | 只由 `scripts/prepare-dsh-compat.mjs` 生成，不手改 |
| `plugin/compat/desktop-022/agent-loop.original.mjs`、同目录 `provenance.json` | 官方 0.2.2-rc.1 包 | 只由 `scripts/prepare-dsh-compat-022.mjs` 生成，不手改 |
| `plugin/compat/agent-loop.mjs` 等兼容副本 | 官方源码的受控改写 | 只做有原生回归覆盖的最小改动；不顺手重构，不混用 master 接口 |
| `plugin/session-client/client.js` | DSH 上游产物 | 视为第三方代码，不重构 |

代码评审和规模统计应排除上述文件。

## 3. 模块与函数

- 一个模块只承担一类职责，文件名用 kebab-case 的 `.mjs`，导出具名函数或工厂，不用默认导出。
- **体量参考线**：新模块宜在 400 行以内；函数宜在 80 行以内。超过 150 行的函数在修改时应优先抽出阶段函数，但不得为了达标而机械切分。参考线不是 CI 门槛，超出时在 PR 中说明原因。
- **先抽纯函数**：与闭包或实例状态无关的校验、转换、计算优先放进独立模块，并直接单测。有状态的编排保留在原所有者内，通过显式参数或小型上下文对象传递依赖。
- 不新增类继承层次、第二套调度器、通用插件框架或“为未来版本”预留的兼容抽象。新能力复用现有模块（如 `replay-buffer`、`run-settlement`、`step-lifecycle`、`catalog-cache-policy`、`observability-*`）。
- `src/backend.mjs` 与 `remote/runtime.mjs` 是编排入口，只做编排：新增功能把规则写进独立模块，再在入口接线，不在入口里继续堆分支。

## 4. 状态、缓存与并发

- 每类缓存或在途请求只能有一个所有者，由它统一提供读取、合并在途请求、代次栅栏和失效等操作。调用方不得在多处直接清空或改写这些内部字段。
- 失效原因要有名字，例如认证复核、换连接、连接关闭或账号边界。新增失效点时，同步更新所有者模块及其测试。
- 异步结果写回前必须核对连接身份、代次或绑定，晚到的旧结果不能覆盖新状态。
- 不得在原本同步的“检查 → 标记 → 派发”之间插入 `await` 或新的微任务边界。重构时保持 `await` 的位置和副作用顺序。
- 计时器、监听器和子进程要有明确的释放路径；重复释放必须幂等。

## 5. 执行语义（不可降级）

- 审批、取消、超时和未知执行结果必须原样传播。有副作用的调用结果未知时不得自动重试，必须先核实。
- 接口不支持的操作要明确报错或禁用，不能假装完成；缺失数据保持未知，不补造、不改写原始 `observedAt`。
- 普通会话走 DSH 原生链路，只有远程会话使用专属预设与执行循环。SDK 独占模型上下文与压缩，不得用 DSH 历史伪造原生恢复。
- 错误使用稳定的大写错误码（`^[A-Z][A-Z0-9_]*$`），面向用户的消息用中文；日志和诊断不得包含凭据、授权 URL、令牌或聊天正文。

## 6. 协议与持久数据

- RPC 方法名、参数、错误码和诊断事件名属于协议。修改协议需要版本或能力协商，旧客户端连接新服务（及反过来）时必须有可预期的降级。
- 账本 schema 只做可忽略的增量扩展；新增枚举值或字段时，确认旧数据仍能读取、旧版本写入的行仍能被正确解释。
- 新增发布文件时，确认 `package.json` 的 `files` 已覆盖（`plugin/`、`src/`、`remote/*.mjs` 按目录或通配收录，`scripts/` 和 `docs/` 按文件列出）。

## 7. 风格

- Node 24 ESM，两空格缩进，单引号；`remote/` 与 `src/` 沿用各文件现有的分号风格，不做全文件格式化改动。
- 超时、周期、容量等数值用具名常量或带单位的参数默认值（如 `timeoutMs = 15_000`），同一含义只在一处定义。
- 避免多层嵌套三元表达式和超长单行；条件超过两层时改成具名变量或 `if`。
- 注释说明“为什么”和不变量，不复述代码；对外导出写一行 JSDoc。

## 8. 测试与检查

- 测试文件为 `test/<模块名>.test.mjs`，使用 `node:test` 与 `node:assert/strict`。新增模块配套直接用例；修复缺陷时补能复现该缺陷的用例。
- **禁止**通过删除、放宽断言或修改预期来让测试通过。重构只能调整 import 路径或等价的访问路径，并在 PR 中逐条列出。
- 测试访问内部字段视为技术债：新代码通过公开操作断言行为，不新增对私有字段的读写。
- 提交前的最小检查：
  - 相关用例：`node --test test/<相关>.test.mjs`；
  - 改动跨模块或属于重构：`node --test test/*.test.mjs`，失败数为 0，通过数不得少于基线；
  - 改动 UI 源码：`node scripts/build-client.mjs --check`。
- 原生行为以当前维护桌面基线的 Windows Electron 检查为准，CI 只运行 0.2.2-rc.1；不为 rc.5 等旧桌面持续扩展适配或发布门槛。已有旧源码和记录暂留用于追溯，旧对话与 SDK 绑定的数据保护独立保留。本机未运行的层要在交付说明中写明。不得为测试安装浏览器、容器或新工具链，不得调用真实模型做常规回归。

## 9. 提交与 PR

- 一个 PR 解决一个问题。重构与功能修改分开提交；纯移动代码的提交不夹带行为变化。
- 提交信息用英文 conventional 风格（`fix:`、`feat:`、`refactor:`、`test:`、`docs:`、`release:`），正文说明动机和不变量。
- PR 描述包括：触发问题、最终行为、实际检查数字、未验证项。不得包含凭据、私有日志、真实机器路径或聊天正文。
- 同一文件的并行修改应串行进行，或先约定接口；大文件重构期间，其他任务避免触碰同一区域。

## 10. 接手检查清单

1. 阅读本规范、[Issue 并行开发与交付](development.md) 和相关模块文档。
2. 核对当前分支、head、未合并 PR 及其 CI，不重复推送、建 PR 或部署。
3. 修改前先读目标模块及其测试，确认状态所有者和执行语义边界。
4. 交付时报告：完成内容、实际检查、未验证限制。合并、发布和两端升级分别需要用户授权。
